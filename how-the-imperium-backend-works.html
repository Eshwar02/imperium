How the Imperium Backend Works

A complete walkthrough — from a git URL to intelligence, transformations, and HITL approval gates.

1 · The Big Picture

The backend is a FastAPI application that wraps a multi-agent intelligence pipeline. You give it a git repository. It clones it, builds a knowledge base across three stores, runs specialist AI agents in parallel, extracts business rules, simulates transformations, and then asks humans to approve changes through two gates before anything is committed.

Everything flows through one entry point — the Orchestrator — which sequences the agents, enforces the approval gates, and writes every decision to an append-only audit log.

2 · Three Storage Layers (fixed contract)

🐘 PostgreSQL
Relational metadata — rkb/store.py
  • repositories
  • modules (+ AI authorship %)
  • business_rules (dedup hash + version)
  • decisions (full HITL audit trail)
  • transformation_priority
  • changeset_manifests + files
  • simulation_results
  • timeline_events
  • test_results
⚡ Qdrant
Semantic memory — rkb/embeddings.py
  • Module summaries
  • Business rule text
  • Timeline event summaries
  • Simulation evidence
  • Hierarchy payload filters:
    repo → domain → module → file → function
🕸 Neo4j
Call + dependency graph — rkb/graph.py
  • Nodes: Function, Class, Module, File, ApiEndpoint, DbTable
  • Edges: CALLS, DEPENDS_ON, EXPOSES, READS, WRITES
  • Blast-radius traversal (up to N hops)
  • React Flow structure map

Postgres and Qdrant are always kept separate by design — relational facts go to Postgres, vector search goes to Qdrant. Alembic manages all Postgres migrations (alembic/versions/001_initial_schema.py).

3 · The Full Pipeline (step by step)

1
POST /api/ingest — Clone & Persist
You send a repo_url + optional ref. The backend clones the repo via GitPython into an isolated workspace at .imperium/workspaces/{repo_id}/, detects languages, writes a Repository row to Postgres, and returns repository_id immediately. The heavy work starts in the background.
PostgresBackgroundTask
2
Knowledge Base Build (background) — Orchestrator.build_knowledge_base()
Runs in the background immediately after ingest. Five sub-steps in sequence:
① Parse — all source files via tree-sitter (with regex fallback) → language-agnostic AST nodes
② Call graph → Neo4j: MERGE Function/Class nodes + CALLS/DEPENDS_ON edges
③ Timeline — walk git log, classify every commit (feature/refactor/incident/dep-shift/test/doc/churn) → Postgres + Qdrant summaries
④ Embed — module summaries embedded via Mistral-embed → Qdrant with hierarchy payload
⑤ Priority scores — 6-factor weighted score per file → transformation_priority table
PostgresNeo4jQdrant
3
POST /api/analysis/{id} — Parallel Agent Analysis
Four agents run concurrently via ThreadPoolExecutor:
• StructureAgent — module map, architecture graph (Cerebras)
• BusinessLogicAgent — implicit rule extraction from AST (Nemotron + Mistral)
• SecurityAgent — CVE/vulnerability scan (Cerebras)
• ResearchAgent — synthesizes timeline + business rules + Qdrant semantic search (Gemini long-context)
All findings merge and are persisted as BusinessRule rows. Modernization findings automatically become rules.
LLMPostgresQdrant
4
HITL Clarifications — GET /api/clarifications/{id}
Rules extracted with confidence < 70% are surfaced as natural-language questions. Developers answer via POST /api/clarifications/{id}/answer. Answers are written back to the BusinessRule row (verified=true, developer_answer). This becomes permanent RKB knowledge — never lost.
Postgres
5
Gate A — POST /api/gate-a (Human Approval)
You review the findings by category (security, performance, modernization, integration, documentation) and cast approve / reject / defer votes. Each vote is persisted as an append-only Decision row with origin=human, the verdict, and the note. Only approved categories advance to transformation.
Postgres (append-only)
6
Simulation + Changeset (intelligence layer)
Before any real change is made:
• Changeset organizer clusters files by module-prefix + shared business rules (union-find) + Neo4j call-graph proximity → ChangesetManifest
• Simulation per file: describe old behavior → generate new code (Codestral) → build unified diff → LLM safety review → confidence score. If confidence < 0.75 → blocked and escalated back to human. Evidence vectors stored in Qdrant.
PostgresNeo4jQdrantCodestral
7
Gate B — POST /api/gate-b (Behavioral Diff Review)
You review the behavioral diff (old behavior → new behavior) + the confidence score for each approved category. Same approve/reject/defer mechanic — persisted as Decision rows with gate=gate-b. Approved categories merge to integration.
Postgres (append-only)
8
Documentation + Comprehension (post-merge)
DocumentationAgent generates: architecture overview (Mermaid graph), business-rule catalog, decision log table, module reference docs — all Markdown, pulled from live RKB data (Groq + Gemini).
ComprehensionAgent generates 3 check questions per Gate-B decision and flags modules with ≥70% AI authorship + low comprehension score back into Gate A review.
Groq / Gemini / CerebrasPostgres

4 · Agent Roster & LLM Routing

Every agent has a fixed role that maps to a provider chain in llm/routing.py. Providers fall through automatically on failure.

ResearchAgent
Gemini (long context)
Reads timeline + business rules + Qdrant semantic hits → synthesizes findings and modernization recommendations.
BusinessLogicAgent
Nemotron → Mistral (fallback)
Extracts implicit rules from code. Core differentiator — finds undocumented limits, guards, clamps, magic constants.
StructureAgent
Cerebras
Builds the module map and structure graph used by the React Flow UI and priority scoring.
SecurityAgent
Cerebras
Scans for CVEs, unsafe patterns, and tech-debt signals. Score feeds into the priority ranking.
ImplementationAgent
Codestral (Mistral)
Generates modernized code. Feeds the simulation dry-run before any real change is written.
DocumentationAgent
Groq → Gemini (fallback)
Produces Markdown + Mermaid architecture, rule catalog, decision log table, module reference.
ComprehensionAgent
Cerebras
Post-Gate-B: 3-question comprehension checks per decision. Flags high-AI-authorship modules for re-review.
CompatibilityAgent & TestingAgent
Cerebras / Mistral
Compatibility gate checking and test-code generation (Phase 1 stubs, wired into pipeline).

5 · Transformation Priority Score (what to modernize first)

Computed for every file after ingestion. Six weighted factors — higher = modernize sooner.

FactorWeightSource
Blast radius (dependents)30%Neo4j traversal
Business rule density20%Postgres business_rules
Low-confidence rules15%Postgres (confidence < 0.7)
AI authorship %15%Module.ai_authorship_pct
Churn (commits/month)10%Timeline events
Security debt findings10%SecurityAgent findings

7 · The Append-Only Decision Log (audit trail)

Every decision — whether made by an agent or a human — is written as a new row in the decisions table. Nothing is ever overwritten. Each row records:

Decision row fields category · change_summary · rule_preserved · alternative_rejected · gate (gate-a / gate-b) · origin (agent / human) · approver · verdict (approve / reject / defer) · prompt_asked · prompt_answer · created_at

This is both the audit trail and the training signal — future runs use it to avoid repeating mistakes.

9 · Memory Hierarchy (how agents remember context)

When an agent needs context, it queries Qdrant with a filter that picks the coarsest level that answers the question, then drills down. This avoids flooding context windows.

Hierarchy encoded as Qdrant payload keys Repository → Domain → Module → File → Function → Paragraph → Statement
Example filter: {"repository_id": "abc", "module": "auth"} → returns only auth-module vectors

10 · How to Start It

1. Set environment variables (copy .env.example → .env, fill in API keys and DB URLs).

2. Start the databases via Docker Compose:

docker compose up -d

3. Run Alembic migration (creates all 10 tables):

cd backend && alembic upgrade head

4. Start the API server:

cd backend && uvicorn imperium.main:app --reload --port 8000

5. Interactive docs: open http://localhost:8000/docs
